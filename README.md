What FlowForge actually is
FlowForge is a project and team management platform built specifically for companies that need controlled access — where people can't just join a project, they have to request access and get approved. Think of it as a combination of Jira (for tasks), Linear (for the UI feel), and an enterprise access control system — all built from scratch as a DevOps training project so you can practice deploying real microservices.
The platform has one core concept: a hierarchy of power. An admin oversees everything. A manager owns projects and decides who gets in. A member works inside the projects they've been granted access to. Nothing crosses those boundaries — the system enforces it technically, not just by convention.

Why microservices instead of one app
The entire point of this project for your DevOps training is that each service is an independent deployable unit. You can update the task service without touching auth. You can scale the project service independently if it gets hammered with approval requests. You can deploy the analytics service separately. Each one has its own database — meaning a corrupted task_db cannot affect logins.
This also means you get to practice: building individual Docker images, writing separate Dockerfiles, managing multiple environment files, handling inter-service communication through a message bus rather than direct calls, and using Kubernetes to orchestrate all of them together.

How the gateway solves the "shared folder" problem
In the original design, there was a shared Python folder with middleware and RBAC decorators that every service imported. The problem is that this creates a deployment dependency — you'd need to mount a shared volume or package it separately, which complicates your Docker images and your CI/CD pipeline.
The solution is to move all that shared responsibility into the gateway. The gateway is the only thing that knows about JWT validation. Once it validates a token, it strips the Authorization header and replaces it with plain HTTP headers: X-User-ID, X-User-Role, X-User-Email, X-User-Org. Every service receives these headers and trusts them — no crypto, no JWT library needed in the downstream services. Each service just reads request.state.user_role from its own small rbac.py middleware, which is just 20 lines of code copied into each service directory. No shared dependency, no shared folder, fully self-contained images.

How the services communicate
There are two communication patterns in this system.
The first is synchronous HTTP via the gateway. The browser sends a request, the gateway validates it and forwards it to a service, the service responds, the gateway streams the response back. This is how all user-facing operations work: logging in, creating a task, fetching the Kanban board.
The second is asynchronous events via Redis. When a member requests access to a project, the project service doesn't wait around to send an email — it publishes a message to a Redis channel called notify.manager and returns a response immediately. A background worker (the SMTP email worker inside auth-service) picks up that message and sends the email without any of the user-facing code caring about it. This decoupling means if your email server is down, the core application keeps working — emails will just be delayed or skipped, but approvals still function.
The analytics aggregation works the same way but uses a Redis Stream (not just Pub/Sub). Every service writes to an audit_log stream whenever anything significant happens. The analytics service runs a consumer group that reads those entries, aggregates them into daily stats, and stores them in analytics_db. This means the analytics service can go down for an hour and, when it comes back up, it replays all the missed events from the stream — nothing is lost.

What each service does in detail
Auth Service is the identity provider. It's the only service that knows passwords or holds the RSA private key. When you log in, it verifies your bcrypt-hashed password, builds a JWT with your user ID, email, role, and organization, signs it with the private key, and returns it. Nobody else in the system ever sees your password. The invite system works by generating a random token, storing it in the database with a 72-hour expiry, and sending an email with a link. When the invited person clicks the link and registers, the token is marked as used and the account is created. The auth service also exposes its public key at /api/auth/public-key — this is how the gateway gets the key it needs to validate JWTs without calling auth-service on every request.
Project Service is the enterprise core. It manages the approval state machine. When a member requests access to a project, an ApprovalRequest record is created with status PENDING. The manager gets notified. When the manager approves, a ProjectMember row is inserted and the member can now see and work in that project. If rejected, the record is updated and the member gets an email explaining the outcome. The service also stores the manager's email and user email in a denormalized way — meaning it doesn't call auth-service to look up names. It stores what it needs at creation time and is self-sufficient.
Task Service is the Kanban engine. It stores tasks with a status field (TODO, IN_PROGRESS, DONE) and enforces transition rules — you cannot move a task directly from TODO to DONE, it must pass through IN_PROGRESS. This rule is enforced in the Python service, not just the frontend. The service also has a position field per task so that when you drag cards around within a column, the order is persisted. Every mutation (create, move, update, delete) appends an entry to the Redis audit_log stream.
Analytics Service is a read-only aggregator. It never writes to any other service's database and never receives direct user actions. Its only job is to consume the audit log stream and answer questions like "how many tasks were created this week?" and "who are the most active users in the last 7 days?". The admin dashboard calls this service to populate its charts and stats. Running this as a separate service means the aggregation work never slows down the services that users interact with directly.

How the frontend fits in
The Next.js app talks only to the gateway on port 8000. It doesn't know the internal addresses of any service — that's intentional. When you log in, the returned JWT is stored in localStorage under the key ff_token. Every subsequent Axios request attaches it as a Bearer token. The gateway validates it and routes the request.
The frontend uses three Axios instances (authApi, projectApi, taskApi, analyticsApi) with base URLs pointing to the gateway, not to individual services. All four point to localhost:8000 — the path prefix (/api/auth/, /api/projects/, etc.) tells the gateway which service to forward to.
TanStack Query handles all caching and re-fetching. When a manager approves a request, the approvals query is invalidated and the list refreshes automatically. When a task is moved on the Kanban board, the board state updates optimistically in the UI first, then the PUT request fires — if it fails, the board reverts.

The Kubernetes layer
In production, everything runs in the noel-ns namespace. Each service runs as a Deployment with 2 replicas and a Horizontal Pod Autoscaler that scales up to 6 pods based on CPU. The gateway is the only service with a public-facing Service (LoadBalancer type) — all others use ClusterIP, meaning they're unreachable from outside the cluster.
The task service uses an Argo Rollouts BlueGreen strategy specifically. This means when you push a new image, Kubernetes spins up a completely new set of pods (the green deployment) alongside the existing ones (blue), routes preview traffic to green, waits 30 seconds after you promote it, then terminates the blue pods. This gives you zero-downtime deployments with an easy rollback path if the new version has issues.

The RS256 key pair — why it matters
This is the most important security concept in the whole system. RS256 is asymmetric cryptography. The auth service holds a private key that signs tokens. The gateway holds only the public key that verifies them. You can hand the public key to anyone — it can only be used to verify, never to forge a new token. This means:

The gateway can validate every JWT locally in microseconds without a network call
Even if an attacker compromises the gateway, they cannot issue new tokens (they'd need the private key)
The private key never leaves the auth-service container

On first boot, if PRIVATE_KEY is empty in the env, auth-service generates a fresh key pair, prints both to stdout, and you copy them into the appropriate .env files. After that, the public key goes into gateway/.env and the private key stays in auth-service/.env only.

Implementation sequence — the right order
You boot postgres and redis first because every service depends on them. Auth-service comes up next and prints the RSA keys — you copy the public key before starting the gateway. Once the gateway has the public key, it can start. Then all other services can come up in any order. The frontend starts with NEXT_PUBLIC_MOCK_MODE=true so you can verify the UI works before wiring it to the real backend, then you flip that flag to false and point it at the gateway.
For Kubernetes: apply the namespace and infrastructure manifests first (postgres, redis), wait for StatefulSet pods to be ready, then apply the service manifests. The Argo Rollout for task-service is applied last and handles all future deploys to that service with zero-downtime flips.
